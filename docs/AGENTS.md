# 通用研发协作与工程约定（智能体协作模板）

本文档是一份**可复用的团队/仓库工程约定模板**，供代码助手（AI 智能体）在任意代码仓库中协作开发时遵循。将本文复制到目标仓库后，可把「项目名、根包名、端口、脚本入口」等占位项替换为实际值即可直接使用。

本文覆盖沟通、工具链、编码、安全、验证与目录管理，所有智能体均应遵守。

## 协作与沟通

- 使用统一的沟通语言（默认中文），称呼与角色由团队约定（如「老大」/「代码助手」）。
- 实施流程遵循：分析 → 计划 → 确认 → 执行 → 测试，涉及实际代码改动前先与用户确认。

## 环境与工具链

- 使用团队约定的 JDK / 构建工具（如 Maven）**固定版本**，均不做自动探测，也不回退到系统默认版本。
- 由开发人员将配置模板（如 `config/toolchain.example.json`）复制为被 Git 忽略的 `config/toolchain.json` 并填写实际路径；或用环境变量（如 `XUYA_JAVA_HOME`、`XUYA_MAVEN_HOME`）覆盖。
- 源码、脚本和文档不得写入开发者个人电脑的实际安装路径；不修改系统默认运行时。

## 统一入口与端口

- 启动、测试、构建、运行、清理等使用**同一套统一脚本入口**，跨平台（Windows / macOS）一致，不保留平台专用启动脚本。
- 各服务使用独立默认端口，端口配置集中在单一配置文件；端口变化需同步代理、允许来源和执行域。
- 端口与进程归属统一由专门的检查脚本判断（Windows 走进程信息，macOS 走 `lsof` + `ps`），**禁止仅凭端口或进程名关闭程序**，必须确认进程归属本工程路径与入口；端口被占用时自动切换空闲端口。

## 编码与跨平台兼容

- 含中文的 PowerShell、VBS 等脚本必须写入 UTF-8 BOM，避免系统默认编码（GBK）导致乱码。
- 跨平台涉及文件读写、命令行参数传递或脚本输出中文时，显式使用 UTF-8，不依赖系统默认编码。
- 提交到 Git 的文档使用英文文件名，保证跨平台路径与编码兼容；本机过程文档不受此限制。
- 可执行文件名与命令拼接需考虑平台差异（`.cmd` / `.sh` / `.exe`），不得写死单平台后缀。
- 启动脚本需校验运行时版本：低于最低要求时给出明确提示，不得回退或误用系统默认旧版本。

## 编码与架构

- 参考阿里巴巴 Java 开发手册（或其他团队选定的规范）：UTF-8、4 空格、显式 import、构造器注入、常量命名和清楚的类注释。
- 分层职责清晰：Controller 处理协议与校验，Service 控制规则与事务，Repository 负责参数化 SQL；DTO、DO、VO 职责区分清楚。
- 产品根包与构建坐标统一为团队约定的命名空间；业务类、模块和产品入口不得使用 Demo、示例工程或占位包名；课程示例、配置模板和测试夹具按真实用途命名。
- 同步 JDBC、文件与 SDK 调用不得阻塞响应式/事件循环（如 WebFlux 事件循环）。

## AI 领域装配与代码执行

- 不同 AI 领域（如教学 AI、开发工作台）从各自工厂独立装配，独立检查真实工具权限，不通过提示词声称禁用机器工具。
- 学习/执行代码按本地可信部署设计，使用管理员选定的主机运行时：每次独立进程/目录，Windows 用 Job Object 限制内存并回收子进程，macOS 用进程树回收。
- 教学 AI 不接入任意宿主 Shell；运行协议不传账户凭证、模型密钥或框架桥接信息。
- 浏览器 Worker 仅保留历史兼容源码，正式入口使用原生运行接口。

## 安全边界

- 密钥不写源码、不发前端、不输出第三方异常正文。
- 测试使用临时数据库和本机模型固定响应，不访问付费 API。
- 本机模型 Key、运行时路径等敏感配置保存在 Git 忽略的本地配置文件中；公共配置只保留环境变量占位。禁止输出 Key、个人安装路径，或将本机配置打入发布包/安装包。

## 前端技术栈

- 统一使用单一前端框架，删除历史/冗余框架源码；前端开发、验证、构建和发布统一使用该框架，默认入口不得指向已废弃框架。

## 验证与交付

- 功能交付需同步 README 和验证记录。
- 前后端、跨平台脚本统一通过约定的验证入口执行（前端测试、运行时测试、后端测试、全栈构建各有对应命令）。
- 前端测试、构建及所有 `npm`/`npx` 命令必须在前端目录下或带 `--prefix` 执行，禁止在根目录直接运行，避免缓存落入根目录。
- 改打包或运行包链路时，需执行打包命令并启动验证。
- 运行器、存储或编辑行为变更需在隔离测试数据上执行浏览器/端到端测试。
- 端到端测试使用自动隔离入口，不手动连接正式服务。

## 阶段边界

- 阶段边界由负责人集中统一安排：日常改动先不考虑移动端适配与桌面打包，这两项留给后续专门阶段统一处理。
- 不要因单个小改动顺手做移动端或打包，避免重复耗费时间精力。
- 浏览器测试与界面验收默认聚焦桌面，除非该次任务明确要求移动端。

## 规划与证据管理

- 产品、课程、技术规划统一维护在本机规划文档（不进 Git）；后续优化直接修改该文件，不新增同级重复规划。
- 主规划区分当前实现与待开发目标；可执行内容与素材在版本化资源中维护，README 记录当前能力，验收结论与证据归本机证据目录（不进 Git）。
- Git 只提交成果性内容（产品能力、规格、契约、可复现步骤与验证结果）；过程、思考、调研、逐条修复史与历史快照不提交 Git。
- 各智能体的中间文件、过程文件、计划方案、草稿与临时产物写入各自的工作目录（以 `.` 开头），不写入文档目录或根目录，并由 `.gitignore` 排除。
- 处理验收、回归、历史结论或「之前怎么验证的」类任务前，先读本机工作区地图与证据目录，不重复造过程文档。
- 文档目录只沉淀成果与结论，开发过程中不频繁更新，通常在 Git 提交前统一整合一次。

## 目录与交付清理

- 保持工程干净：各模块源码、依赖、锁文件、格式配置、脚本、日志与产物归各自模块；根目录只保留入口说明、开发约定与共享编辑器/Git 配置。
- 中间文件、过程文档与缓存按产生者归属：各模块产生的放各自模块目录；各智能体产生的放各自以 `.` 开头的目录，禁止散落到根目录或其他模块目录。
- 提交到 Git 的文档集中在文档目录；规划文档在本机规划目录。
- 数据、日志、正式产物、生成资源分别归各自约定目录，禁止写入源码目录。
- 每次交付前清理自己创建的临时脚本、下载副本、测试库、截图副本和编译缓存；必要的验证证据先分类归档，再检查根目录及 git status。
- 清理脚本只清理模块内中间产物（构建目录、临时缓存等），保留正式包、依赖、数据、日志；根目录依赖不在其清理范围，需单独确认后人工删除。
- 清理仅操作已确认归属的中间产物；保留源码、锁文件、正式交付包、真实数据库与学习记录。不得把 `.gitignore` 当作清理动作，也不得忽略所有 Markdown 或 SQL。

## Git 纪律

- 不修改其他示例/无关项目。
- 不自行提交或推送 Git，除非用户明确要求。
